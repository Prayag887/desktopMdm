# Managed device security boundaries

- The Windows service uses only the documented `/api/agent/` HTTPS endpoints: one-time serial enrollment, authenticated check-in, current-patch fetch, and acknowledgement. It does not store admin-panel credentials.
- The installer requires administrator access. Program Files protects the installed binaries. `%PROGRAMDATA%\EmiDeviceAgent\config.json` contains the device bearer token and is ACL-limited to SYSTEM and Administrators; ordinary users receive only read access to UI-safe state and health files.
- The GUI's health refresh requests UAC approval to run the local companion. Denial is reported; it is not bypassed.
- An administrator retains sign-in and uninstall access. `install.cmd` disables built-in WinRE after installation; elevated `reagentc /enable` restores it, and external recovery media remains available. Absolute uninstall prevention and operating-system lockout are not implemented.
- Anti-theft persistence after reset is an enterprise deployment property, not an agent feature. Autopilot registration/profile assignment, Intune enrollment and Required-app targeting, BitLocker escrow, and model-specific DFCI policy are tenant/OEM prerequisites. See `docs/enterprise-antitheft-deployment.md`.
- BitLocker protects the confidentiality of data on a removed SSD. It does not prevent someone with physical control from erasing, replacing, or destroying the storage device. After a replacement disk or clean install, management returns only if online Windows OOBE recognizes a valid Autopilot registration and Intune can deploy the required application.
- DFCI must be supported by the exact device/OEM channel. The agent never claims DFCI coverage, changes boot security generically or substitutes a BIOS password for tenant-managed firmware policy.
- BIOS manufacturer/model detection is read-only. Local BIOS administrator-password set/change is available only through documented OEM interfaces: Dell Command | Configure, HP CMSL, Lenovo WMI (change only), and ASUS ACT on compatible models. Acer and unsupported models use the explicit UEFI-restart fallback; no guessed generic firmware command is executed.
- BIOS fields are masked, never logged or transmitted, cleared on submission/tab exit, and held in zeroizing Rust buffers where practical. For UAC, plaintext is sent over a local child-process stdin to Windows DPAPI; only machine-scoped DPAPI ciphertext is staged in the current user's protected temporary directory, and both the UI and elevated helper delete it after use. Machine scope permits an administrator account entered at UAC to decrypt the handoff. The elevated helper necessarily materializes plaintext briefly in memory, and Dell/ASUS vendor CLIs necessarily receive it as a process argument; an administrator able to inspect process memory or command lines during that short window may observe it. GUI/text-input and allocator copies cannot be guaranteed erased.
- BIOS changes require UAC approval and the existing password when the OEM reports one is set. The workflow never bypasses, recovers, removes, or guesses a forgotten password. OEM firmware policy, password character rules, supported models, and reboot requirements still apply.
- Payment-restriction mode shows a branded screen (not a fake BSOD), never invokes crash APIs or makes itself unkillable. The `install.cmd` wrapper separately disables WinRE. The service persists the last confirmed server state and checks immediately at startup/resume and every 60 seconds. The UI has no local lock/release controls. See `docs/payment-restriction-architecture.md`.
- The current API has no `LOST` action. A reported-lost device can use `LOCK` with a non-sensitive return message until a versioned API contract adds explicit lost/recovered states. A missed check-in alone must not trigger a lock, and location collection is outside the current contract.
- Lock state follows the admin panel: every check-in's `lock_state` (received over HTTPS with the device's own bearer token) is applied locally, so an admin `LOCK`/`UNLOCK` takes effect on the next check-in (at most ~60 s) without depending on patch signing. Pending commands are still fetched, applied and acknowledged so the admin panel records delivery. When a command-signing key is provisioned (`install.ps1 -CommandSigningKeyId -CommandSigningPublicKey`), a patch is additionally accepted only if `signed_payload` is a valid Ed25519 signature from that `signing_key_id` over the canonical message (device, command, patch, version, action, reason, nonce, expiries, checksum, size), and a durable ledger rejects rollback, equal-version substitution and nonce replay; failures are acked with a reason. Without a key, a patch must still match the pending command UUID/action, be unexpired, and match its API-supplied size and SHA-256 digest.
- An admin-panel `LOCK` shows the fullscreen lock screen for every account on the PC, Windows administrators included. While locked, the service checks every 15 s that the desktop UI is running in the active console session and, if it was closed or never started, launches it there with the signed-in user's own token. Release is the admin `UNLOCK` (applied on the next check-in) or an offline recovery token.
- Enforced mode activates only when the app is launched as the enrolled user's Winlogon shell AND the account is not a local administrator. It then auto-enters the restriction screen, hides the Exit button, holds fullscreen, and vetoes Alt+F4 / window-close (`CancelClose`). It never auto-times-out; release is via an owner-signed unlock token, an administrator signing into their own never-restricted account, or administrator-controlled external recovery media.
- Emergency unlock tokens are Ed25519-signed offline by the owner's private key; their verification does not require API connectivity. Each token is bound to one device id, carries a short expiry and a monotonic counter (persisted by the service in `recovery-state.json`) for rollback/replay protection, and is rejected fail-safe on any error. The admin API remains authoritative: a device still in `LOCKED` state is restricted again after a local emergency release. Crypto is in `crates/emi-core/src/recovery.rs`; the installer provisions `recovery-public-key.hex`; the known lab key is rejected. The shared-word fallback is removed. The service commits the counter and receipt together before the UI can unlock. Missing/corrupt recovery state or a stopped service requires administrator recovery.
- The app cannot block OS-global Alt+Tab, Win, or Ctrl+Shift+Esc — no user-mode app can. Those require the Windows Keyboard Filter (WEKF) feature applied by `Set-PaymentRestriction.ps1` on Enterprise/Education/IoT. Within the app, Escape and Alt+F4 are neutralized and key/text events are drained except in the recovery field.
- Keyboard suppression in the prototype is window-scoped only: the app drains its own key/text events on the restriction screen EXCEPT while the recovery field has focus, so the customer can always type a recovery code and accessibility stays usable. It does not and cannot block OS-global Alt+Tab/Win/Ctrl+Shift+Esc; production uses the Windows Keyboard Filter (WEKF) feature for that, never a custom keyboard driver. The keyboard is never fully disabled.
- Payment schedules remain domain types, not an implemented storage/editor/payment-processing system. Do not treat local files as payment confirmation from a financial provider.
- Existing historical files and previous releases are retained. Updated initialization preserves complete current enrollment, discards incomplete legacy credentials, and keeps the local UUID.
- The optional WinGet bootstrap downloads from Microsoft's official endpoint. Use SkipWingetBootstrap for offline installation; the Rust app itself does not require WinGet.
- The release workflow requires `CODE_SIGN_PFX_BASE64` / `CODE_SIGN_PFX_PASSWORD` secrets and the `CODE_SIGN_CERT_SHA1` repository variable, verifies the resulting publisher and timestamp, and refuses unsigned publication. Signing establishes publisher identity (and cuts SmartScreen "unknown publisher") but does NOT stop behaviour-based AV detection: the app's keyboard hook, Task Manager policy, shell replacement and lockscreen legitimately look like lockware, so on managed devices you must also allow-list the signed app via Defender/MDM. Windows CI compilation/tests do not replace a real GUI/UAC/service/resume smoke test.
